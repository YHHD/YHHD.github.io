从 Claude Code 看 Agent 系统的六个层次

目录 · 4 节

一个能跑的 Agent 原型往往只需要“模型 + 几把工具 + 一个循环”。但要让它在真实终端里长期工作，复杂度会迅速扩散到启动、上下文装配、权限、并发、错误恢复和状态管理。

Claude Code 的公开源码资料提供了一个比较完整的观察样本。它大致可以拆成六层：

层 职责
入口层 初始化环境、配置和会话类型
展示层 React + Ink 构建终端 UI
核心引擎 QueryEngine 管理对话、工具调用与上下文
执行层 Tool System 与 Command System
协作层 多 Agent 与远程桥接
管理层 权限、配置、状态和费用

启动阶段为什么也重要

终端工具每天会被频繁启动。密钥读取、API 预连接、功能开关和 MCP 连接如果完全串行，首屏等待会不断累积。因此启动不是简单的 main()，而是一条明确的状态机：先完成最低限度的可用初始化，再逐步启用依赖网络和外部进程的能力。

QueryEngine 是“胖核心”

QueryEngine 不只负责调用模型。它还管理流式响应、工具分发、自动重试、Token 计数、上下文压缩和停止条件。

这类核心模块通常会显得很大，因为跨轮次状态被拆散之后，调用顺序会变得难以推理。合理的目标不是机械地拆小文件，而是明确哪些状态必须留在同一个事务边界里。

工具面就是权限面

每个工具除了 schema 和执行函数，还应该声明：

isReadOnly: boolean
isConcurrencySafe: boolean
isDestructive: boolean
needsUserInteraction: boolean

没有明确声明的能力，系统应当按更危险的方向处理。文件编辑工具还应该在执行层强制“先读再改”，而不是只把这句话写进提示词。

权限判断也不是一道布尔题，而是一条管道：拒绝规则、询问规则、工具自身检查、当前模式和永久允许依次参与，最后才决定是否执行。

对自建 Agent 的三个启发

  1. 先画边界，再给能力。 工具描述和 schema 不是文档，而是模型可见的行为面。
  2. 把上下文装配当工程问题。 稳定的前缀有利于缓存，动态部分应该明确标注来源和生命周期。
  3. 权限不能只靠提示词。 真正危险的限制必须由调用链和文件系统层强制执行。

Claude Code 的架构不一定适合所有 Agent，但它清楚地说明了：Agent 系统的可靠性，最终来自模型能力之外的工程约束。
